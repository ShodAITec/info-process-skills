# 技术选型评估

## 输入

用户给出**要解决的技术问题**，可能带或不带候选方案：
- 带候选：「向量数据库选 Pinecone、Qdrant 还是 pgvector」
- 不带：「我们要做 RAG 的向量检索，怎么选」——此时你先检索确定 3–5 个主流候选，含至少一个自建/开源选项

务必先明确**约束条件**。用户没说就在报告开头列出你的假设，并标明这些假设会改变结论。

## 交付

一份决策材料：评分矩阵 + TCO + 风险 + 推荐。要能直接拿进选型会。

## 执行步骤

1. **澄清决策**：真正要解决什么问题、什么是硬约束（合规、数据驻留、团队技能、预算、时间）。
2. **确定候选集**：3–5 个，必须包含「自建/开源」和「采购/托管」两类，否则对比不成立。
3. **定评分维度与权重**：先定权重再评分。权重必须显式给出并说明理由——这是整份评估里最主观的一步，必须可被质疑。
4. **逐项取证**：官方文档、基准测试、生产案例、故障复盘、社区 issue。**基准测试要注明是谁做的**——厂商自测与第三方测试分量不同。
5. **算 TCO**：见 `rules/tco.md`。只算许可/订阅费是典型错误。
6. **评锁定与迁移成本**：进去容易出来难的，要在这里暴露。
7. **给推荐**：一个主选 + 一个备选，并写出**什么情况下结论会反转**。

## 不可破坏的约束

- **权重先于评分**。先看分数再调权重凑结论，是这类评估最常见的作弊方式。权重和理由必须写在评分表之前。
- **性能数字必须注明测试条件**。不同数据规模、硬件、并发下的数字不可比。拿不到可比口径就不要并列。
- **TCO 要标注假设**。规模假设（QPS、数据量、席位数）直接决定结论，必须显式写出。
- **必须写反对意见**。对推荐方案列出最强的三条反对理由。只有优点的评估没有价值。
- 开源方案要查许可证与商业条款变更史（近年多起 BSL/SSPL 改许可事件直接改变了选型结论）。
